# Storage and migrations

Read before touching `tasks.ts`, `migrations/`, a schema change, or a `Store` method. The current tables, columns and indexes are in the `// ── Schema` block of `tasks.ts`; this file holds the store's behaviour and invariants.

## Store

Tasks live in a single SQLite database; the path comes from the `TASKS_DB` env var. `tasks.ts` owns the schema and exports every store type.

- **Ids**: `tasks` uses `INTEGER PRIMARY KEY AUTOINCREMENT`, ids come from `lastInsertRowid`. The earlier `meta.counter` scheme drifted whenever an external writer inserted a row without bumping the counter and was dropped in `20260519000000_drop-meta-counter-autoincrement-tasks`. Deleted ids are never reused (the AUTOINCREMENT high-water mark in `sqlite_sequence`).
- **Plans**: go in via `update`/`add({ plan })`, come back via `getById`. There is no file upload: `uploadPlan` was removed in #466 (a remote server can't read client paths; not worth keeping for stdio alone). `mcp/planText.ts` checks every MCP plan write — strict UTF-8, no control chars but tab/LF/CR, BOM stripped, CRLF → LF so `replace()` anchors match. UI REST edits skip it.
- **Refs and notes**: `readTask` adds each ref's target `title` (one JOIN); list reads via `attachRefs` stay title-free, and the zod `refsSchema` strips `title` on input so echoed refs round-trip. `readTask` attaches full `notes`; `attachRefs` adds only `noteCount` (one grouped COUNT), so list reads and `load()` get counts, never bodies. Both fields are omitted when a task has no notes. Each note mutation bumps the parent's `updated_at` in the same transaction.
- **Epics (#312)**: `tasks.parent_id` is a self-FK `ON DELETE SET NULL`, so deleting an epic detaches its children. In a table rebuild the self-FK must be written `tasks(id)`, not `tasks_new(id)` — SQLite doesn't repoint a self-reference on RENAME; `migrations.test.ts` asserts `foreign_key_list(tasks)` targets `tasks`. `assertParent` (inside the add/update transaction, only when a patch touches `type`, `parentId` or the project) throws `Validation failed: …` for: parent missing, parent not an epic, parent in another project, epic with a parent (no nesting; also blocks retyping a child into an epic), retyping an epic that still has children or moving it to another project. Scope invariant (#499): a child's scope always equals its epic's — `add`/`update` silently replace a passed scope with the epic's (on every update of a child, not just link changes), and changing an epic's scope rewrites its children's (any status) in the same transaction. Refs: `applyRefsImpl` rejects a newly added ref to another project, but keeps legacy cross-project refs on the full-list resend every edit does (a project move can still create one). `parentId: null` clears, `undefined` keeps.
  - Epic injection lives in `getById` only, not `readTask` — `update()` and `getRelated` reuse `readTask` and the update echo must stay slim. A child gets `epic` (full text + all notes), an epic gets `children`. List reads and `readTask` carry only `parentId` + `epicTitle` (one bulk title query in `attachRefs`); `toListTask` strips `epic`/`children` as a guard. `getNext` excludes epics in SQL.
  - `syncEpicStatus` runs inside the store transaction of `setStatus` (only on a real status change), `add` with a `parentId`, `update` that changes `parentId` (old epic and new) and `delete` of a child: a child going `in_progress` moves the epic to `in_progress` (reopening a done epic); the epic closes when it has children and all are done; moving a child back to `todo`/`plan`/`refinement` leaves the epic as it is. It lives in the store, not the handler, so UI changes sync too. `handleSetStatus` runs in one `store.db.transaction` (better-sqlite3 nests it as a savepoint) and reports a change as `epicStatus` by comparing the epic's status before and after.
- **External ticket ID (#366)**: `Task.externalId` is the one optional that is **always present** (`null` when unset) — `rowToTask` sets it in the literal; don't move it to the `if (row.x)` pattern, agents rely on the key. Not unique (an epic and its children may share one). `getByExternalId` is case-insensitive exact (`lower()` = ASCII-only folding), all statuses incl. done.
- **Pull requests (#516)**: `task_prs` rows, attached in both `readTask` and `attachRefs` (one grouped query) because the card tags need them on list reads; omitted when empty. `update({ prs })` replaces the whole list like refs (`null`/`[]` clears, `undefined` keeps); `applyPrs` carries each surviving url's `created_at` over, so the list order (by `created_at`) survives status changes. `validatePrs` (http(s) url, integer number > 0, known status, url unique per task) runs before the transaction, also for UI REST writes. Status is whatever an agent last wrote: nothing polls the git host.
- **Projects**: see `projects.md`.

## Connection and concurrency

- Journal mode is `DELETE` (the SQLite default). WAL's mmap'd shm region isn't coherent across host/container bind mounts — readers stay on stale snapshots until checkpoint, which breaks SSE live updates in a consumer reading the DB through a bind mount. DELETE coordinates via POSIX advisory locks on the main DB file, which is bind-mount-safe. Write contention is a non-issue at this scale.
- `busy_timeout=5000`: DELETE journaling raises immediate `SQLITE_BUSY` without it (the health handler's read-only connection uses `2000`).
- `foreign_keys=ON` is wrapped in `try/finally` around `runMigrations` so a thrown migration can't leave the connection with FK enforcement off — that would silently break the `refs` ON DELETE CASCADE.
- `runMigrations` runs in a single `BEGIN IMMEDIATE` transaction so two processes calling `createStore` on a fresh DB serialise on the write lock instead of both racing into duplicate `schema_migrations` INSERTs (the bundled-mode UI spawns right after the MCP's `createStore`). The loser waits on `busy_timeout`, then sees the populated table and the loop becomes a no-op.
- **Pre-migration backup (#368):** inside that transaction, once pending migrations are known and before the first `up()`, a non-fresh file DB is copied (`copyFileSync`, `COPYFILE_EXCL`) to `<db>.backup-<local stamp>-pre-<first pending>`, with one stderr line. It must stay a file copy under the lock: `VACUUM INTO` can't run inside a transaction, and a backup taken before the lock races (every opener would copy). The copy is consistent because `journal_mode=DELETE` leaves the main file untouched until commit. A failed copy throws, so nothing is migrated. Backups are never pruned.
- `schema_migrations` is the gate; `PRAGMA user_version` is kept in sync with the migration count for backward compat but is NOT used as a gating check. The downgrade guard throws `StaleSchemaError` for applied names with no file on disk (`staleSchemaMessage` carries the rebuild/restart fix).
- **Stale-schema guard during a session (#368):** another process can migrate the DB while this one runs, and the open-time check can't see that. Every Store write method calls `assertSchemaCurrent()` first (one `SELECT` on `schema_migrations` against the names `runMigrations` returned). Reads are deliberately allowed. **A new write method must call it too.** The MCP's `withSchemaCheck` (`mcp/shared.ts`, wrapping every tool in `registerTools`) turns `StaleSchemaError` into a tool error and appends a ⚠ restart line to read results. The UI router maps it to 409, and the client shows the message via `failureReason`.

## Adding a schema change

1. New file `migrations/YYYYMMDDHHMMSS_kebab-slug.ts`.
2. `export const name = 'YYYYMMDDHHMMSS_kebab-slug'` — must match the filename stem exactly (the runner enforces this).
3. `export function up(db: Database): void` with forward-only SQL.
4. Update the `// ── Schema` block in `tasks.ts` to the new shape in the same commit.
5. Run `npm run verify` in both `simple-task-manager` and `task-manager-ui` before committing.

Never squash or delete applied migrations: the downgrade guard rejects a DB whose applied names are missing on disk.

- **FKs are OFF during the migration loop.** `runMigrations` disables `foreign_keys` before applying anything, re-enables it after, then runs `PRAGMA foreign_key_check`. Without this, table-rebuild migrations (CREATE-new / INSERT…SELECT / DROP / RENAME) trigger ON DELETE CASCADE during the DROP and wipe `refs` and `notes`. Don't toggle `foreign_keys` inside `up()` (no-op inside a transaction).
- **Table rebuilds must restore `sqlite_sequence`**: `DROP TABLE tasks` deletes its row and the rebuild reseeds it from the highest *surviving* id, so the ids of deleted top tasks would be handed out again. `add-projects` reads `seq` before and writes `max(old, new)` back; the older rebuilds didn't (already applied, left alone).
- **Widening a CHECK-constrained enum** (a new `status` or `type`) needs a full table rebuild — SQLite can't ALTER a CHECK constraint. `20260519010000_add-plan-status` is the canonical pattern: CREATE `tasks_new` with the expanded constraint, `INSERT … SELECT … FROM tasks ORDER BY id`, DROP, RENAME, recreate indexes. Then add the value to every enumeration site: the `TaskStatus`/`TaskType` union in `tasks.ts`, the zod schemas in `mcp/registerTools.ts`, the duplicated union in `task-manager-ui/src/types/task.ts`, plus UI constants (`TYPES`/`TYPE_ORDER`/`TYPE_LABELS` in `src/client/constants.ts` and the private `TYPE_ORDER` in `src/lib/taskView.ts` for a type; `STATUS_LABELS`, `STATUS_NEXT`, `STATUS_CLASSES`, `STATUS_RANK`, `STATUS_ORDER`, `STATUSES`, `INITIAL_STATUSES`).
- **Migration tests** that seed "every migration before X" must filter `m.name < X`, not `m.name !== X` — the latter also applies every *later* migration before X runs, which a table-rebuild migration then silently drops.

## Consumers of the `Store` surface

`tasks.ts` is the only source of the store, with two consumers: `mcp/*` and `task-manager-ui/src/server/taskStore.ts`, which imports it via a relative path (`'../../../tasks.js'`) — there is **no vendor mirror** and no `EXPECTED_MIGRATIONS` list; the UI picks schema changes up at the next tsx import. There is no compile-time link between the two packages: when you add/rename/remove a `Store` method, grep `task-manager-ui` for the old name and update its wrapper.
